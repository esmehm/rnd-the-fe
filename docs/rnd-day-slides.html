Rewrite the front end?

Can we — and can we prove it?

Thin React perf bake-off  ·  behaviour-anchored parity testing

The problem

A rewrite is on the table — for good reason

Old low-spec tablets (Lenovo M10) in end-client hands are near-unusable. A full front-end rewrite has been proposed.

Two ways a rewrite goes wrong — the two things worth de-risking before anyone commits:

  • It turns out not actually faster — or you can't say what made it faster.
  • You can't prove the new app still does what the old one did.

→ Two strands: measure the win  +  prove parity.

Strand A · Performance

Can we win without leaving React + TypeScript?

A pure-JS prototype already showed the performance ceiling is high — but it got there by dropping React and type-safety.

So the useful question isn't "can it be faster" — it's:

  • Can we capture most of that win while keeping React + TS? — dev + AI familiarity, JSONForms binding, plugins, lower risk.
  • And where does the win come from?

"Drop React?" becomes a separate, later, evidence-based decision — not the premise of the rewrite.

Strand A · The control-arm setup

Keep React. Rip out everything that's slow.

Remove

  • MUI + emotion (runtime CSS-in-JS)
  • Material React Table

Replace with

  • React Aria — headless a11y
  • vanilla-extract — zero-runtime CSS
  • TanStack Table + Virtual
  • React 19 + Compiler · Rspack · kept TS

Greenfield stocktake screen, real backend — measured against the current app at 6× CPU (M10 proxy), prod builds.

Strand A · The reframe

It was the libraries — not React's renderer.

The ~4× / ~5.6× win holds with the VDOM still in place.

So we take the low-risk win now — keep React + TS, dev + AI familiarity, the JSONForms/plugin ecosystem.

The React → Solid/Svelte swap drops from mandatory to an optional, later bet — with headroom still on the table.

Strand B · Testing

Prove parity without doubling QA

  • Behaviour IDs = single source of truth. Every rule QA checked by hand is now an atomic, ID'd behaviour (OMS-REG-INV-03.9). ~112 case files migrated + a CI guard.
  • Two engines, same anchor: a deterministic Playwright suite (covers-tagged) and an exploratory AI agent — both anchor to the same IDs; neither redefines them.
  • The old app is the oracle. Both FEs run on one unchanged backend → the rewrite becomes differential testing.

Strand B · The money slide

The parity matrix

Same spec, BASE_URL-swapped. One cell per behaviour:

passes on OLDfails on OLD
passes on NEW✅ replicated⚠️ old bug fixed — confirm intended
fails on NEW🔴 regression the rewrite introducedknown-broken — not a blocker

The 🔴 cell is the blocker list. "Done" stops being "feels close" → every active behaviour green on new, at visual parity, within perf budget.

Strand B · Do the tests survive a rewrite?

Portability is a property of the DOM, not the framework

Measured on the distribution workflow:

  • ~98% semantic locators — getByRole (90), getByTestId (55), getByText (27).
  • vs 3 brittle (CSS-hash / nth-child).

Any FE that emits a queryable, accessible DOM + preserved data-testids keeps the suite. (Failure mode: a <canvas>/WebGL grid → no DOM → every locator dies at once.)

So a stack bake-off doubles as a portability check — this is the bridge to Strand A.

Strand B · Proof it bites real catch

The exploratory agent found a real bug in the rewrite

Pointed at the new FE, it walked the full stocktake workflow (~24 behaviours) in ~26 min and found 5 issues, including:

  • HIGH — Add-item double-count (data integrity): finalising an added item that already has stock posts a new stock line on top → 500 in stock, counted 450, finalised as 950. DB-verified. Root-caused to the FE.
  • + a validation/error-leak (MEDIUM-HIGH) and 3 LOWs; each anchored to a behaviour ID.

The kind of bug perf metrics, type-checks and load tests never see — caught in ~26 min. The strand catches real new bugs, not just replays known ones.

  • Strand B → any rewrite is done — and its portability check is how you'd pick the stack.

Takeaway

A rewrite is justified when you can
measure the win and prove parity.

We can drastically improve performance without leaving React + TypeScript — and prove the new app matches the old with tests that don't care which front end they're pointed at.
